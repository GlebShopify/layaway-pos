Discount = the register’s repricing leverExtensions can’t run cart transforms at POS; a fixed discount (= balance) makes checkout charge exactly the deposit as a normal sale.

◆ Why one shape (the key constraint)

Pay now = full outstanding, alwaysOnline customers can’t pay partial amounts against an order — so orders must start small and grow.
Custom line item = customer-set amount→ instantly generates a real checkout for exactly that much.
Ledger = source of truthReal total vs paid lives in the metafield; order total is a payment record.

⚠ Landmines

  • Reporting / exports must read the ledger, not order totals
  • Scopes: read_all_orders · write_order_edits · write_cart_transforms
  • Poll after orderEditCommit (no read-after-write guarantee)
  • Order edits must use the presentment currency (CAD ≠ shop USD)
  • Deposit discount stays visible on every POS-order pay screen
✖ Retired vs. first prototype:  native POS split-tender partial payment (created a full-outstanding order online customers could only pay in full) · two order shapes · “partially paid” badge as the status source — replaced by the ledger + unified deposit shape.
